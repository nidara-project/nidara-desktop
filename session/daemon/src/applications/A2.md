# Applications1 A2: launch and autostart preferences

A2 extends the opt-in `nidara-sessiond --applications` service from A1. The
installed session, TS UI, compositor, configuration registry, system grants and
CI configuration are unchanged. This implementation depends on IPC B locally;
publication/installation of either block is a separate decision.

## Admission, identity and observations

`Launch(epoch, desktopId, generation, request)` returns an admitted LaunchId,
not a successful window or focus acknowledgement. The closed request accepts
Mode (`activate`, `new-window`, `action`, `open`), Action for action mode, Uris
for open mode, ActivationToken and RequestId. Defaults to activate. Invalid
combinations, unknown keys/types/NUL, more than 128 URIs or 256 KiB URI text,
tokens over 8 KiB and RequestIds over 128 bytes fail before admission.
`OpenDirectory` accepts an absolute local existing directory URI and only
ActivationToken/RequestId context. It resolves the current inode/directory
handler at admission. It does not open arbitrary resources through xdg-open.

Trash is a fixed exception for the dock: Launch the current DefaultDirectoryApp
in open mode with exactly `trash:///`; it must declare directory handling and
URI support. Other trash resources or a stale handler fail. OpenDirectory
itself remains restricted to local directories. No physical Trash path or
TS/Exec bypass substitutes for an unavailable handler.

App generation, source desktop hash and the original kernel-authenticated Peer
are rechecked before each effect. Metadata-only entries without Exec or D-Bus
activation are retained as unavailable. GIO accepts such entries but can return
a NULL executable; its nullable C result is checked before conversion, avoiding
gio-rs' non-optional PathBuf wrapper. D-Bus-only desktop entries use a synthetic
Exec only during GIO metadata parsing, never as a launch fallback.

AppLaunch permits native Shell/Launcher; external callers need computer-control.
AppAutostart permits native Shell/Settings; external callers need both control
and config-write. Neither grants Spawn, focus/window control or privilege to
the CLI. Checkout paths receive no new grant. Worker revalidation catches
revocation while queued and before each multi-file invocation.

There are at most 32 active records and eight workers. Worker time, including
queueing, is bounded to 9 s; visual observation expires at 10 s. Records and
same-sender RequestIds remain for 30 s, at most 64 nonces per sender and 1024
records globally. Identical arguments return the original LaunchId even after
catalogue changes; different arguments with the same nonce fail Conflict.
There is no retry after timeout, owner replacement or ambiguous delivery.
Tokens are private to a plan and its selected destination; only a digest is
retained for the bounded replay check. A multi-%f/%u launch gives the token to
the first invocation only. No token, URI list or expanded argv is published in
metadata/status or emitted in logs. Remote error bodies are never copied into
launch status because they can echo private data.

GetLaunch returns State (`accepted`, `dispatched`, `failed`,
`timed-out-unknown`), EffectStarted, DispatchFinished, OutcomeUnknown, Error,
canonical identity/generation, DispatchUnits and ActualUnit. Dispatched means
all systemd start jobs completed or the application D-Bus call returned, not that
a window appeared. DispatchFinished lets the CLI keep its original PID alive
through deferred authorization. DispatchUnits records queued units immediately,
while State stays accepted until every start job completes successfully.
FocusConfirmed, WindowConfirmed and
PortalIdentityVerified remain false. Removal/generation changes terminate
pending observation; late completion cannot resurrect a terminal state.
Successful dispatch still expires to unknown observation without H1/A3; no
window correlation, usage/new marker or focus policy is invented here.

Use `LaunchAvailable` and capability `launch` (`open-directory` for folders).
`LauncherAvailable` is the separate, still-unavailable Unity integration.
ResolveWindow and AcknowledgeNew remain unavailable.

## Exec, terminals and D-Bus activation

Exec follows desktop-entry argv/field-code rules with bounded parsing and no
shell expansion. `%f/%u` produce one invocation per item, `%F/%U` produce a
vector; `%c`, `%k`, `%i` and `%%` expand once. Invalid/quoted field codes,
multiple file codes, unsupported URI schemes and remote paths for file fields
fail explicitly. Non-UTF-8 executable/local-file/cwd paths fail Unsupported
rather than changing the filename through lossy conversion. Declared actions
use their action Exec; new-window honors SingleMainWindow and declared actions,
otherwise reports relaunch/unsupported explicitly.

The backend calls the systemd user manager's StartTransientUnit directly. This
is the managed-service equivalent allowed by the contract after reviewing
uwsm's implementation; there is no extra helper process that inherits the
shell's unit or transports a token in argv. Properties include Type=exec,
ExitType=cgroup, app-graphical.slice, CollectMode=inactive-or-failed, canonical
SourcePath and escaped desktop identity in `app-<desktop>@<launch>.service`.
ExecStartEx uses `no-env-expand` so literal `$` arguments remain literal.
WorkingDirectory is desktop Path or HOME, stdin null and output journal.
An explicit environment allowlist forwards session/display/locale variables;
UnsetEnvironment removes inherited invocation, fd/pressure/watchdog and startup
credentials. GTK_THEME=Empty is removed for children, including a manager's
inherited value. An explicit non-Empty user theme remains respected.

Each Exec plan has its own bus connection and subscribes to JobRemoved before
starting units, avoiding subscription races between concurrent launches. Start
job failure is visible, and observation has the same overall deadline. A missing
manager is Unavailable; an uncertain call/job result remains unknown. The
reported DispatchUnits are the actual requested service names, not proof that
portal identity or the app's final process/cgroup has been verified.

Terminal=true wraps the payload with a configured installed TerminalEmulator
entry, respecting desktop-specific/ordinary xdg-terminals.list preference and
exclusions, its Exec and terminal execution argument (default -e). It runs in
the same managed unit with the payload's canonical desktop identity. Unsupported
terminal/D-Bus combinations fail; there is no arbitrary command-string helper.

DBusActivatable uses the exact desktop bus identity and standard object path.
Activate/Open/ActivateAction receive the per-launch activation-token platform
data. Legacy desktop-startup-id/DESKTOP_STARTUP_ID forwarding is not implemented
or validated for X11/Xwayland clients. An absent owner is activated through
StartServiceByName, with a fresh
permission check before that effect and the subsequent application call. The
selected unique owner is pinned. Missing activation, refusal and timeout never
fall back to Exec. An existing owner's actual unit is read through its bus PID
and GetUnitByPID/Unit.Id when available; otherwise ActualUnit remains unknown.
It never reports an Exec helper's unit as the existing application's identity.

Primary references: [desktop Exec rules](https://specifications.freedesktop.org/desktop-entry/latest/exec-variables.html),
[application D-Bus activation](https://specifications.freedesktop.org/desktop-entry/latest/dbus.html),
[systemd manager API](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.systemd1.html),
and [systemd desktop integration](https://github.com/systemd/systemd/blob/main/docs/DESKTOP_ENVIRONMENTS.md).

## XDG autostart preference ownership

A2 indexes effective XDG_CONFIG_HOME/autostart and XDG_CONFIG_DIRS/autostart
entries with basename precedence, Hidden, OnlyShowIn/NotShowIn, TryExec,
X-GNOME-Autostart-enabled and X-systemd-skip. The index is bounded to 512 entries,
256 KiB each and 4 MiB total; incomplete reads disable writes. Per-app Autostart
reports Available, Writable, PreferenceEnabled, AppliesToDesktop, Enabled,
Reason and Started=false. A saved preference is not a claim of execution.

SetAutostart copies the effective matching desktop entry into the user's
canonical basename, preserving localized/unknown keys/comments, and changes
Hidden plus its canonical identity marker. Enabling also restores
X-GNOME-Autostart-enabled=true in the user copy, so an older tool's false value
cannot silently defeat the requested preference. It never edits the system entry or
deletes the user's file. Exclusive 0600 temporary creation, fsync/rename and
readback bound the write; symlink parents/leaves and foreign/read-only user
files fail. Different Exec/identity at that basename or an existing matching
entry under another filename gives Conflict, rather than overwriting unrelated
state or creating duplicate autostarts.

The existing uwsm XDG autostart target/generator remains the sole executor.
Applications1 never runs an autostart loop on startup/restart. D-Bus, Terminal,
Flatpak and Snap autostart remain Unavailable until their session-start and
portal/terminal fixtures establish that route. TS's existing Lua preference
editor is unchanged; A2 does not migrate or create a second Lua runner.

## Validation and remaining acceptance

```
cargo build --manifest-path session/Cargo.toml --workspace --locked
cargo test --manifest-path session/Cargo.toml -p nidara-sessiond --bin nidara-sessiond --test applications --test applications2 --test config --locked
cargo test --manifest-path session/Cargo.toml -p nidara-ipc --locked
cargo test --manifest-path crates/nidara-access/Cargo.toml --offline
cargo clippy --manifest-path session/Cargo.toml --workspace --all-targets --locked -- -D warnings
```

The A2 fixture uses private XDG roots, settings, a real private bus, fake systemd
and disposable actual Python applications. It checks literal argv/env/cwd/unit
properties, field multiplicity/token single delivery/replay, actions/new-window,
real private bus activation/Open/ActivateAction, actual-owner unit lookup through
a fake manager, failed job/refusal/timeout, default directory/Trash, CLI routing,
original-peer queued revocation, nonce/generation behavior and typed autostart
preservation/collisions/symlink/read-only gates. The installed XDG generator is
run only into private output directories to verify enable/Hidden precedence;
no generated unit is started. The ready object is registered before its bus name is published, so immediate
NameOwnerChanged hydration does not race UnknownObject. A1 retains its private catalogue/icon/layout,
owner/epoch/consent/root-outage and Exec-less regression coverage.

The applications2 Cargo test builds its sibling nidara-ipc in the daemon's
profile/target directory before running the fixture, so it can be invoked alone.
For direct Python invocation, build both workspace binaries first. Evidence
always lives under the source worktree's target/applications1, independently of
CARGO_TARGET_DIR; only disposable runtime sockets use
/tmp. These checks do not validate the real user manager/cgroup lifecycle,
portal attribution, installed app launches or login autostart, physical input
tokens, terminal appearance, dock bounce/focus, hardware or voiced Orca. Those
require separately authorized acceptance in the relevant session; no install or
live-session change is performed here.
